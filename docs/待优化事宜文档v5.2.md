# Terax 待优化事宜文档 v5.2

> 状态：待评估、待执行。
>
> 本文记录当前 D 盘代码的 GPU/内存审计结论，并规划 JSONL、CSV、PDF、图片和日志文本的低内存阅览路线。本文只定义边界和实现策略，不视为已经完成的代码改动。

## 一、当前问题结论

### 1. WebView2 GPU 占用的实际归因

本次现场核验捕获到的运行进程为：

| 项目 | 现场值 |
|---|---|
| Terax 主进程 | `C:\Users\79988\AppData\Local\Terax\terax.exe` |
| WebView2 GPU 子进程 | PID `26768`，命令参数含 `--type=gpu-process` |
| WebView2 数据目录 | `C:\Users\79988\AppData\Local\app.crynta.terax\EBWebView` |
| GPU Process Memory | Shared `126.2MB`，Total Committed `131.59MB` |

现场运行的是 C 盘已安装版本，尚未证明是 `D:\software\terax-ai-main` 目录中的 exe。迁移源码目录不会改变 WebView2 的用户数据目录，也不会自动改变已安装程序的启动来源；后续性能对比必须先确认进程 `ExecutablePath`。

当前配置和代码中存在明确的 WebGL 链路：

- `src/modules/settings/store.ts` 的 `terminalWebglEnabled` 默认值为 `true`。
- `src/modules/terminal/lib/rendererPool.ts` 引入 `@xterm/addon-webgl`，终端槽激活后会创建 WebGL context、字符图集纹理和 canvas。
- 渲染池最多保留 5 个终端槽，WebGL 槽位隐藏后还有 30 秒回收宽限期。
- `src-tauri/tauri.windows.conf.json` 启用了透明无边框窗口，WebView2 需要额外维护合成表面。
- 当前设置界面没有显示 WebGL 开关，`setTerminalWebglEnabled` 只剩底层 setter，默认值实际成为隐式强制开启。

文件树、CodeMirror、Markdown、普通 CSS UI 和 PTY 通信没有发现需要 WebGL 的业务逻辑。高额 GPU 分配主要来自终端 WebGL 与透明窗口合成，WebView2 GPU 进程本身的基础分配也包含在系统统计中。这个数值代表图形资源提交/共享，不等价于持续的 GPU 运算负载。

### 2. GPU 精简路线

#### P0：关闭 WebGL 默认路径

将 `terminalWebglEnabled` 默认值改为 `false`，并增加一次性迁移，把历史 `true` 配置转换为 `false`。重启后先测量 WebView2 GPU Process Memory，确认下降幅度。

终端继续使用 xterm 的标准渲染路径，保留 PTY、PowerShell、Bash、Zsh、Fish、TUI、滚动、搜索和多终端功能。此步骤改动小，适合先验证因果关系。

#### P1：确认下降后移除 WebGL 组成

如果 P0 能明显降低 GPU 占用，继续删除：

- `@xterm/addon-webgl` 依赖和 import；
- `webglAddon`、`webglCanvases` 字段；
- `attachWebgl`、`disposeSlotWebgl`、context loss 恢复和 canvas context 释放；
- `WEBGL_REAP_GRACE_MS`、`applyWebglPreference` 及孤立的设置字段。

这一步能从架构上保证 Terax 不创建终端 WebGL context，减少维护代码和浏览器 GPU 状态不确定性。

#### P2：仅在 P1 后仍偏高时处理透明合成

评估把 Windows 窗口从 `transparent: true` 改为不透明背景，同时保留 `decorations: false` 和现有自绘标题栏。此步骤可能影响圆角边缘和窗口阴影，必须单独做视觉回归，不能和 WebGL 删除混在一次改动中。

不建议为了降低这 100MB 替换 WebView2。Terax 的 HTML/CSS/React UI、CodeMirror 和 xterm 都依赖 WebView2；替换运行时会变成重写整个桌面渲染层，成本和风险远高于收益。

## 二、现有文件读取链路的内存问题

当前 `src-tauri/src/modules/fs/file.rs` 的默认文本读取上限是 10MB，强制打开上限是 50MB。读取流程会经历：Rust `Vec<u8>` → UTF-8 `String` → IPC 序列化 → React 状态 → CodeMirror 文档；编辑器还会保留 saved buffer 和当前 buffer。

`src/modules/editor/lib/useDocument.ts` 和 `EditorPane.tsx` 对普通文本适合小文件，但不适合大日志、JSONL、CSV：

- `fs_read_file` 会一次性读取完整文件；
- CodeMirror 需要建立完整文档；
- 搜索状态会调用 `toString()` 并创建大小写副本；
- `EditorStack` 会让所有已打开且非 cold 的普通编辑器保持挂载；
- `MarkdownStack` 同样保持所有 Markdown 预览挂载；
- `MarkdownPreviewPane` 会把完整 Markdown 交给 Streamdown，文档越大 DOM 越重。

因此，新增文件格式时不能简单地把文件扩展名加入现有编辑器。低内存方案必须先限制读取范围，再决定是否建立完整编辑模型。

## 三、文件预览能力的统一定位

### 1. 已有能力与缺口

`EditorPane.tsx` 已经可以通过 `convertFileSrc` 预览 PNG、JPG、GIF、WebP、SVG、ICO、视频、音频和 PDF。PDF 当前使用 WebView2 的 iframe，图片使用本地 asset URL，没有把文件转成 base64；这条基础路线应保留。

目前缺少的是：

- JSONL 的逐行结构化阅览；
- CSV/TSV 的有限行表格阅览；
- 大型日志和普通文本的窗口化阅览；
- 图片/PDF 只在当前标签激活时加载和销毁；
- 非活动标签的编辑器和 Markdown 内容回收策略。

### 2. 推荐的查看器分流

| 类型 | 默认视图 | 内存边界 | 交互原则 |
|---|---|---|---|
| 普通代码/小文本 | CodeMirror | 延续现有 10MB 默认读取 | 保持编辑、保存、搜索 |
| JSONL | 只读逐行预览 | 首屏最多 200 行或 1MB | 每行独立解析，解析失败显示原文；提供“原始文本”入口 |
| CSV/TSV | 只读表格预览 | 首屏最多 200 行、40 列或 1MB | 后端/前端流式解析，不构造全量二维数组；提供“原始文本”入口 |
| `.log`/大型 `.txt` | 虚拟化日志查看器 | 按字节窗口读取，首屏最多 1MB | 只渲染可见行，支持上下滚动窗口和轻量搜索 |
| 图片 | 原生 `<img>` asset URL | 只加载当前激活标签 | 禁止 base64；大图显示尺寸和加载状态，必要时生成缩略图 |
| PDF | 原生 WebView2 PDF iframe | 只挂载当前激活标签 | 不引入 PDF.js；关闭标签立即卸载 iframe |

## 四、推荐的低内存预览接口

新增一个窄接口即可覆盖 JSONL、CSV、日志和大文本，不扩展成通用文件服务：

```text
fs_read_text_window(
  path,
  offset_bytes,
  max_bytes,
  max_lines,
  workspace
) -> {
  content,
  start_offset,
  next_offset,
  start_line,
  end_line,
  total_bytes,
  has_more,
  mtime
}
```

后端使用 `BufReader` 或等价的固定缓冲区读取，保证单次内存上限；UTF-8 截断在字符边界修正，不把整个文件读入内存。前端只保留当前窗口和一个前后滚动缓冲窗口，切换文件或窗口时取消旧请求。

JSONL 和 CSV 的解析应优先在后端按行/记录流式处理，只返回首屏需要的记录。前端不保存完整 JSON 对象数组，也不把 CSV 全量转换成 DOM table。对于超过首屏上限的内容，顶部显示“已加载范围 / 文件总大小”。

## 五、标签和阅览器内存策略

保留用户标签语义，同时减少隐藏视图：

1. 当前激活文件始终挂载。
2. 非激活且未修改的代码文件允许卸载 CodeMirror，标签只保留路径、标题和 dirty=false；再次激活时重新读取。
3. 非激活 Markdown 预览直接卸载，Markdown 不需要保留运行中的 DOM。
4. dirty 文件不能自动卸载，避免丢失内存中的未保存内容。
5. PDF iframe、图片元素和结构化预览只为当前激活标签创建。
6. 不改变现有双阅览器语义，每个阅览器组独立执行上述回收策略。

这比单纯降低文件大小上限更有效，因为当前 `EditorStack`/`MarkdownStack` 会让多个非活动标签保持完整组件树。

## 六、执行顺序与验收标准

### 第一步：GPU 因果验证

- 确认启动进程来自 `D:\software\terax-ai-main`，避免把 C 盘安装版当成 D 盘版本测量。
- 临时关闭 WebGL，重启并记录 WebView2 GPU Process Memory。
- 比较无终端、单终端、TUI 静止和持续刷新的四种状态。

### 第二步：WebGL 精简

- 默认关闭并迁移旧配置；
- 通过同一版本对比 GPU Shared/Total Committed；
- 终端功能回归后移除 WebGL 代码和依赖；
- 保留最后一个便携版作为回滚基线。

### 第三步：低内存文件预览

- 1GB JSONL：首屏打开不读取全文件，滚动按窗口加载；
- 500MB CSV：首屏表格只产生有限记录和列；
- 100MB 日志：滚动和搜索不建立完整 CodeMirror 文档；
- 大图片：不转 base64，不预加载非活动标签；
- PDF：只挂载当前 iframe，切换标签后释放；
- 现有 JS/Python/Markdown 编辑、保存、双栏对照和终端不回归。

## 七、最终决策建议

当前最优路径是“先关 WebGL验证，再删除 WebGL；随后建立窗口化文本预览和活动标签回收”。

不建议同时引入 PDF.js、重量级 CSV/JSON 可视化框架、全量索引、预加载缩略图缓存或后台文件扫描。这些组件会重新制造当前项目正在清理的内存和注意力负担。

v5.2 的核心边界：

- WebView2 保留，WebGL 终端移除；
- 普通代码继续 CodeMirror，数据/日志文件走受限预览；
- PDF/图片复用原生 URL 能力，避免 base64 和重复缓存；
- 所有非活动阅览器允许回收，dirty 文件保留；
- 任何预览都先限制字节、行数、列数和并发，再扩展能力。
