# 资源档案隔离：实验结论与实施边界

日期：2026-09-18；实测本机 codex-cli 0.153.4。本轮不修改产品实现。

## 实验方法

实验脚本 `.reference-cache/resource_probe.py` 使用临时 CODEX_HOME、本地 HTTP Responses SSE 假上游和 fake-a/fake-b 两个假 key。真实 config.toml/auth.json 只检查结构，不输出真实 key，不修改文件，不调用真实模型。进程环境分别注入 key，启动参数覆盖同名 provider 的 base_url、env_key、requires_openai_auth。实验进程已清理。

用户实际配置：model_provider=pipixia，wire_api=responses，requires_openai_auth=true，auth.json 中存在 OPENAI_API_KEY。资源档案模式可在 Codev 子进程内切换到 env_key 认证、requires_openai_auth=false，保持 provider ID 与 Responses 协议，不改变原生文件。

## 结果

| 项目 | 结果 |
| --- | --- |
| 固定 pipixia，A/B 使用不同 baseURL/key | 各自命中 /a/v1/responses + fake-a、/b/v1/responses + fake-b |
| A 的轮次挂起，B 新建线程发送 | B 完成；释放 A 后 A 也正常完成 |
| A 空闲线程取消订阅，再由 B 恢复同一 ID | 失败：already has an active writer |
| 取消订阅后等待即时 thread/closed | 40 秒未发生；版本源码默认卸载延迟为 30 分钟 |
| A 全部完成、退出 A，B 恢复同一 ID | 成功，provider=pipixia，历史含 A 的第一轮 |
| B 完成、退出 B，再由新 A 恢复同一 ID | 成功，含 A/B 两轮；第三次模型请求包含此前两轮输入 |
| model/list 是否查询假上游 | 返回 6 个目录模型，上游请求数为 0 |

源码：`codex-rs/app-server/src/request_processors/thread_lifecycle.rs`，rust-v0.153.4 的 THREAD_UNLOADING_DELAY = 30 * 60 秒。当前稳定 ClientRequest 没有即时单线程 close/unload 接口。取消订阅不等于释放写锁；config 覆盖不能绕过另一个进程持有的写锁。

因此，之前“空闲线程下一次输入即可立即切到另一资源进程”的判断不成立。不能用复制历史、改写 session 文件、临时归档原线程来冒充无损迁移。

## 存储与界面确定方案

采用 `$CODEX_HOME/codev.json`（本机 C:/Users/79988/.codex/codev.json）。不要把第三方凭据档案扩展进 Codex 的 config.toml；即使某版本接受未知字段，也不等于官方保证其兼容和保留。JSON 文件本身不提供加密。

文件仅持有 version、activeResourceId、resources 数组。每项保存 id、alias、baseUrl、encryptedKey、revision；当前 Windows 用 DPAPI 当前用户保护 key，Rust 解密并仅注入目标子进程环境。前端列表只接收掩码，编辑时空 key 表示不修改。明文编辑输入不写日志、命令行或 UI 布局文件。DPAPI 文件复制到另一用户/机器不能直接解密，需要重新录入 key。

provider 为有效原生配置中读取的只读值，当前显示 pipixia；启动时明确固定该 ID，不能由项目层或档案自定义覆盖。初次配置只读取原生配置为默认资源，保存副本必须明确由用户操作；不自动覆盖 auth.json。若外部修改 provider，暂停新资源调度并提示重新加载原生设置，避免静默混用。

设置入口位于顶部线程栏折叠按钮旁，面板包含“服务商存储”Tab，列表显示别名、base_url、掩码 key，以及添加、编辑、删除、探测。provider 固定只读。资源下拉放在多视口按钮左侧，选择表示后续轮次的默认资源；每个运行中会话显示实际使用资源，避免全局选择与正在运行的资源混淆。编辑使用中的档案创建新 revision，旧请求沿用旧快照。

模型不作为资源档案的必填配置。app-server model/list 只能提供其目录，不能作为上游支持能力证明。可选 GET /models 只用于辅助发现；真实可用性必须通过用户点击的最小 Responses 探测确认，并显示可能消耗少量额度。未提供 /models 的服务不能直接判定不可用。最近模型/思考等级按资源档案记忆，新线程继承；恢复线程优先保留原模型，不静默替换。

## 两条可交付路线

### A. 坚持按资源共享 app-server（最小改造）

相同有效 provider/baseURL/key 复用进程，不同资源按需启动。全局切换后新线程立即进入 B，A 上运行/审批/启动中的会话继续由 A 处理，steer/interrupt/审批响应仍绑定原连接。

旧线程的下一轮若要迁移到 B：在 A 尚有其他活动任务时显示“等待原资源释放”，保留草稿；A 所有任务完成后退出 A，释放写锁，再在 B 原 ID 恢复并发送。该限制必须进入产品文案，不能宣称任意空闲线程即时切换。模型调用完成之外还需纳入后台命令与待审批状态，不能只看前端 busy 标记。

### B. 严格满足用户描述的下一轮即时切换（需要改变架构）

保持线程所在 app-server 不迁移，以按需本地路由代理持有 baseURL/key。每个线程有稳定路由标识，每个轮次开始时绑定选定资源的不可变快照；运行中的所有后续请求、重试和工具后的模型请求继续使用该快照，下一轮再采用最新全局选择。

不能仅实现全局代理目标切换，因为一轮任务可能发起多次模型请求，那会使运行中的任务中途换资源。代理需要覆盖取消、SSE、连接认证及 WebSocket 复用行为，并验证线程路由标识可靠传递；这一完整路径本轮尚未实验，不能宣称已经可用。它保留官方 runtime，不引入每线程进程，但超出最初“资源进程池”方案，需要用户选择后实施。

结论：当前官方版本的原生资源进程池可以确定交付 A；用户要求的全部即时切换语义不能仅凭固定 provider 和进程池实现。若必须完整保留这些语义，应先验证 B 的逐轮路由，再施工。
