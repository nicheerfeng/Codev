# 单线程解锁探测

日期：2026-09-18。版本：本机 Codex CLI 0.153.4。结论：单线程正常关闭并释放写锁的底层机制可行；不能把强删锁文件作为可靠迁移实现。无副作用的公开即时卸载接口仍缺失，需要最小 Codex 补丁才能明确提供此能力。

## 隔离实测

脚本 `.reference-cache/lock_probe.py` 使用临时 CODEX_HOME、本地假 Responses 上游、假 key，无真实模型调用。仅删除了实验目录的锁文件，未操作用户会话或安装版进程。实验子进程均已回收。

1. A 加载线程 T，完成一轮；A 的另一独立线程 S 保持运行。
2. 删除 T 的 `.lock`：本机 Windows 上成功；B 恢复 T 也成功。
3. 查询 A/B 的 `thread/loaded/list`：两者都仍加载 T。该结果只证明可绕过锁，不证明无损迁移；未让两个写入器并发写数据。
4. 为避免污染结论，正常关闭实验使用新的线程 U。B 直接恢复 U 首先报 active writer。
5. A 调用 U 的 `thread/archive`，再 `thread/unarchive`，B 随后恢复 U：成功。归档/恢复/接管合计约 0.108 秒（本地微型假数据，不是性能承诺）。U 原 ID 保留，历史一轮保留；B 新一轮完成。
6. A 中 S 始终保留，释放假上游等待后正常完成。

## 对应源码

上游 tag rust-v0.153.4：

- `thread-store/src/local/writer_lock.rs`：持有文件句柄并调用 `File::try_lock()`；删除锁路径并不会终止旧线程写入器。
- `thread-store/src/local/live_writer.rs` 的 `shutdown_thread`：关闭 recorder、同步历史路径、移除 live recorder；写锁 guard 随对象释放。
- `app-server/src/request_processors/thread_lifecycle.rs` 的 `wait_for_thread_shutdown` / `unload_thread_without_subscribers`：按线程关闭、按实例匹配移除 runtime、发出 thread/closed，失败不应被视为迁移成功。
- `app-server/src/request_processors/thread_processor.rs` 的归档路径调用正常 shutdown，但会收集并归档 spawned descendants。因此不能将“临时归档再恢复”无条件包装成用户不可见的切资源操作。

## 可行补丁边界

为 app-server 增加专用单线程 unload 请求，复用正常 shutdown 路径并等待完成；不修改历史、不归档、不删除锁文件。卸载前通过线程操作协调避免与 start/steer/审批竞争；仅接受空闲、无待处理审批及相关活动任务的线程，多订阅者时拒绝；成功后更新订阅/监听状态并回复。Codev 收到完成响应后才在 B resume；异常时保留原状态，不强行接管。

源码和正常关闭实验支持这个方向，但本轮没有编译带新接口的 Codex 二进制，不能声称补丁完成验证。交付此路线需要维护版本固定的 Codev 专用 Codex 构建与升级验证。

## 不二开时的妥协

多视口期间明确禁用资源选择器，提示“退出多视口并等待所有任务结束后切换”，不能静默忽略用户选择。还须检查后台任务：退出多视口并不终止隐藏会话，所以只检查窗口数量不足以保证安全。所有旧 runtime 任务结束后关闭该进程、释放写锁，再启动新资源并恢复历史。

当前产品尚未实现资源档案与资源选择器；它们仍处于方案阶段。本轮没有新增无实际资源切换行为的占位禁用按钮，也没有修改模型选择器或沙箱选择器。
