# 模型记忆与凭据切换调研

调研日期：2026-09-18。本轮仅实施沙箱默认完全访问及移除继承配置菜单；下述模型记忆与凭据切换仍为设计方案。

## 当前代码

`client.ts` 中 model 选项保存在当前线程的内存 Session；发送时交给 `turn/start.model`，历史初始模型来自 `Thread.model`。`create(cwd)` 未读取最近使用模型，也未传入 `thread/start.model`。Pi 则通过 `store.ts` 的 `piAgentLastModel` 持久化并在新线程使用。因此目前支持单线程下轮换模型，不具备跨线程的最近模型记忆。

Rust 的 `CodexAgentState.process` 只有一个进程槽，所有 Codex 视口共享一个 app-server。它继承启动环境，当前没有 Codev 凭据档案、运行时重载或本地代理功能。

## 已核对的上游实现

cc-switch 本地参考位于 `.reference-cache/cc-switch`，提交 `06082e189d65e6d6dbadc35dacdac1ce6c79d89a`。

- `src-tauri/src/services/provider/mod.rs` 的 `switch`：普通模式写 live 配置；代理接管模式调用 `hot_switch_provider_inner`。
- `src-tauri/src/services/proxy.rs`：接管时维持 Codex 的本地代理入口，并更新当前供应商和相关配置。
- `src-tauri/src/proxy/handler_context.rs`：每次创建请求上下文时选择供应商。
- `src-tauri/src/proxy/provider_router.rs`：读取当前供应商配置；故障转移为另一独立功能。
- `src-tauri/src/proxy/providers/codex.rs`：提取真实 baseURL 和认证信息，为上游构建认证头。

这证明其代理模式可以在请求边界改变上游；不能据此承诺已经打开的流式连接会迁移到另一服务端。

官方 app-server 文档将 `config/value/write` 和 `config/batchWrite` 定义为配置文件写入。`turn/start` 可覆盖 model，但当前生成协议没有 key/baseURL/modelProvider 参数。`thread/resume` 有 config/modelProvider 覆盖，但不能假设它总是重建已加载线程。

核对本机版本对应的官方 `rust-v0.153.4` 源码 `codex-rs/app-server/src/request_processors/thread_processor.rs`：已加载线程存在订阅者时会保留重加入语义，并警告忽略 override；无订阅者、空闲且关闭成功时才可进入冷恢复路径。这不是一个通用的凭据热重载保证。使用 env_key 的凭据还涉及进程启动环境。

## 建议实施顺序

1. 最近模型记忆：按 provider/凭据档案记录最近模型及思考等级，新线程显式传入；旧线程保留自己的模型。目标上游未提供该模型时要求重新选择，不静默替换。
2. 凭据档案：固定 provider ID，每个档案持有名称、baseURL、凭据引用；真实 key 不进入布局记忆和日志。由 Rust 给本插件子进程注入凭据环境及配置覆盖，不改写用户 Codex Desktop 的全局配置。
3. 首版采用全局运行时重载：选择新档案后，等所有活动轮次结束，再结束本插件的 app-server；用新凭据重新启动和握手。保留 Codev 中的草稿、历史、视口和标题，下一次发送时恢复相应原生线程。运行中选择仅标记待切换；立即停止需独立明确操作。

此方案无需关闭 Codev，但会重建原生运行时，运行时内的后台终端、MCP 连接等不能承诺原样保留。当前共享进程不适合把重载包装成只影响一个视口的操作。

若后续明确要求不同视口同时使用不同凭据，再单独设计按凭据档案隔离进程。若明确要求 app-server 也不重启，则采用按需本地代理：Codex 固定连接本地地址，代理在新请求上选择 key/baseURL；已有请求保持原上游。该路线还需处理 SSE、WebSocket、取消和上游续传状态，实施成本更高，当前不建议一并引入自动故障转移或协议转换。
