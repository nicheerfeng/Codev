## 问题 001：顶层根文件夹右键缺少新建入口

### 现象

在侧边栏已经加入工作区的顶层根文件夹上右键，例如截图中的
`epid_query_v8_main`，菜单可以显示“添加文件夹到工作区”“新建终端”“复制路径”“从工作区移除”，但没有“新建文件”和“新建文件夹”。

当前只能通过工作区顶部工具栏的新建按钮创建根目录下的文件或文件夹。

### 复现路径

1. 将一个项目文件夹加入工作区。
2. 在侧边栏顶层根文件夹标题行右键。
3. 观察菜单缺少“新建文件”和“新建文件夹”。
4. 点击顶部新建按钮，功能可以正常进入创建流程。

### 当前代码定位

`src/modules/explorer/FileExplorer.tsx` 的 `RootSection` 负责顶层根标题右键菜单。目前该菜单包含：

- 添加文件夹到工作区
- 新建终端
- 复制路径
- 从工作区移除

`RootTreeHandle` 已经暴露 `createFile()` 和 `createFolder()`，并且 `FileExplorer` 已通过 `treeRefs` 保存每个根目录对应的树实例。因此创建能力已经存在，缺口集中在顶层根标题菜单没有连接这两个句柄。

### 候选解决方案

集中优化时给 `RootSection` 增加两个回调：

```text
onCreateFile
onCreateFolder
```

渲染顶层根标题菜单时调用当前根对应的：

```text
treeRefs.current.get(root)?.createFile()
treeRefs.current.get(root)?.createFolder()
```

建议菜单顺序：

1. 新建文件
2. 新建文件夹
3. 分隔线
4. 添加文件夹到工作区
5. 新建终端
6. 复制路径
7. 从工作区移除

这样可以复用现有的内联创建流程，不增加新的后端命令，也不会改变顶部按钮、文件行右键菜单和空白区域菜单。

### 集中优化验收条件

- 每个顶层根文件夹右键都显示“新建文件”和“新建文件夹”。
- 在多项目工作区中，右键哪个根目录，就在哪个根目录下创建。
- 创建后以内联输入形式出现在对应根目录第一层。
- 取消、重名、刷新和已有文件夹右键菜单行为保持正常。
- 空白区域右键仍只承担工作区级菜单语义，不混入根目录创建误触。

### 当前结论

问题已完成记录和初步定位，当前没有修改代码，等待晚间集中优化。

## 问题 002：终端导航列表不支持上下拖拽排序

### 现象

右侧终端导航区目前按照终端标签数组顺序垂直展示，例如截图中的
`epid_query_v8_main`、`shiny`、`流病agent项目`。终端可以点击切换、双击或 F2 重命名、右键关闭，但无法通过拖拽调整上下顺序。

用户希望直接拖动某个终端条目，在导航列表中移动到目标位置，形成稳定的个人工作顺序。

### 复现路径

1. 打开两个或更多终端。
2. 在右侧终端导航列表按住某个终端条目。
3. 向上或向下拖动到另一条目附近。
4. 当前条目不会出现拖拽状态、落点提示，也不会改变顺序。

### 当前代码定位

`src/modules/terminal/TerminalPanel.tsx` 的导航区使用 `tabs.map(...)` 直接渲染终端条目，目前只有点击、双击、键盘和右键事件，没有拖拽状态或落点计算。

终端顺序来源于 `App.tsx` 的 `terminalTabs`，底层状态由 `src/modules/tabs/lib/useTabs.ts` 维护。项目已经存在可复用的 `reorderTabByGroup()` 和 `reorderTabsByGroup()`，可以在限定终端 ID 集合后重排，不需要新建终端数据结构。

`src/modules/spaces/lib/serialize.ts` 会按 `tabs` 当前顺序序列化终端标签，因此重排后的顺序可以跟随现有工作区持久化链路保存。

### 增量候选方案

第一步只增加“当前工作区终端导航列表内部排序”：

1. `App.tsx` 向 `TerminalPanel` 增加 `onReorder(fromId, toGapIndex)` 回调。
2. 回调内部复用 `reorderTabByGroup(terminalTabs.map(tab => tab.id), fromId, toGapIndex)`。
3. `TerminalPanel.tsx` 复用文件标签栏已有的 Pointer Drag 思路，增加纵向落点计算。
4. 拖动过程中显示一条主题色横向落点线，释放时只改变终端标签数组顺序。
5. 终端条目中的关闭按钮、重命名输入框和右键菜单标记为不可拖拽区域，避免操作冲突。

首期不改变终端内部的左右/上下分屏结构，不跨工作区移动终端，也不引入 HTML5 原生拖拽数据传输。这样可以复用已有状态和持久化机制，改动集中在导航列表交互。

### 集中优化验收条件

- 可以把任意终端拖到列表顶部、中间和底部。
- 拖动时有清晰的横向落点提示，释放后顺序立即稳定。
- 当前激活终端保持不变，重排不重启 PTY、不丢失输入内容。
- 关闭、重命名、右键菜单和终端运行态动画不受影响。
- 重启应用或切换工作区后，终端顺序按最近一次排列恢复。
- 终端内部的分屏顺序与导航列表排序逻辑保持独立。

### 当前结论

问题已完成记录和增量方案设计，当前没有修改代码，等待晚间集中优化。

## 问题 003：多项目顶层根目录区分度不足

### 现象

当工作区同时加入多个项目时，顶层根目录标题行基本使用同一套前景色和背景色，项目数量增加后不容易快速识别。截图中多个项目根目录与普通文件树内容的视觉层级接近，注意力需要反复确认项目名称。

用户希望只增强顶层根目录的识别度，自动补充低饱和、偏莫兰迪风格的文本色和轻背景色；子文件夹、文件和文件内容保持现有颜色体系。

### 当前代码定位

`src/modules/explorer/FileExplorer.tsx` 的 `RootSection` 负责渲染顶层根目录标题。目前所有根目录共享：

- 活跃状态：`bg-accent/60 text-accent-foreground`
- 非活跃状态：`text-foreground/80 hover:bg-muted/50`

根目录列表由 `roots.map(...)` 顺序渲染，当前没有根目录颜色映射，也没有项目级视觉标识。

### 增量候选方案

1. 增加一组固定的莫兰迪色板，例如灰蓝、灰青、鼠尾草绿、藕紫、陶土和暖灰。
2. 使用规范化根路径生成稳定哈希，将每个根目录映射到色板索引；颜色跟随路径稳定，不因添加、删除或排序其他项目而整体换色。
3. 只给 `RootSection` 标题行应用颜色：非活跃根目录使用很低透明度背景和柔和文本色，活跃根目录提高背景透明度并保留清晰文字对比。
4. 子树区域不继承根颜色，文件夹、文件图标、选中态和内容阅读器继续沿用主题默认样式。
5. 颜色通过主题变量或 `color-mix` 与当前主题背景混合，兼容深色、浅色和现有 Codev 主题，避免直接使用高饱和纯色。

首期只增加顶层标题行的文本色、轻背景色或窄侧边色带，不增加图例、设置项或额外颜色管理界面。

### 集中优化验收条件

- 多个项目根目录可以一眼区分，颜色整体低饱和、柔和且不抢夺文件内容注意力。
- 深色和浅色主题下文字均保持清晰对比。
- 只有顶层根目录标题行改变，一级及更深层文件树颜色保持原样。
- 项目加入、移除、排序和重启后，同一绝对路径尽量保持同一颜色。
- 根目录展开、折叠、选中、右键菜单和工作区切换行为不受影响。

### 当前结论

问题已完成记录和增量方案设计，当前没有修改代码，等待晚间集中优化。

## 问题 004：文件树、阅读视口和终端的宽度约束不够合理

### 现象

当前三块区域都可以拖拽，但文件树存在固定最大宽度，终端和中间阅读区主要依赖百分比下限。大型项目、长文件名、宽表格或终端 TUI 同时出现时，用户无法把需要的侧边区域继续拉宽；反过来，侧边区域变宽后中间阅读区也可能被压缩到不适合阅读的尺寸。

用户希望文件树、阅读视口和右侧终端能够根据当前任务自由扩展，同时有稳定、低认知负担的恢复路径。

### 当前代码定位

`src/app/App.tsx` 当前采用两层横向可拖拽布局：

| 区域 | 当前约束 |
|---|---|
| 文件树 | 默认使用已保存宽度，最小 `220px`，最大固定 `480px`，可折叠到 `0` |
| 工作区 | 外层默认 `78%`，最小 `30%` |
| 中间阅读区 | 内层默认 `70%`，最小 `30%` |
| 右侧终端 | 内层默认 `30%`，最小 `10%`，可折叠到 `0` |

`src/modules/sidebar/useSidebarPanel.ts` 会持久化文件树宽度，但会把它裁剪到 `220px–480px`。右侧终端当前只保存折叠状态，没有持久化最后一次展开宽度。

Header 已常驻提供左侧文件树切换按钮和右侧终端切换按钮，因此两个侧栏都有明确的恢复入口。

### 方案判断

采用三面板同层约束模型：文件树、中心阅读区、右侧终端处于同一个横向 `ResizablePanelGroup` 中。中心阅读区的最小宽度固定为 `60px`，不再保留当前 `30%` 的相对下限。

设应用内容区宽度为 `W`，文件树当前宽度为 `L`，终端当前宽度为 `T`，两个分隔条总宽度为 `H`，中心阅读区为 `C`：

```text
C = W - L - T - H
C >= 60px

文件树可向右拉到：Lmax = W - T - H - 60px
终端可向左拉到：Tmax = W - L - H - 60px
```

拖动文件树分隔条时，终端保持当前宽度不变，只有中心阅读区缩小；拖动终端分隔条时，文件树保持当前宽度不变，只有中心阅读区缩小。这样与用户给出的计算逻辑完全一致。

首次启动仍保留文件树和终端的初始种子宽度，后续以用户最近一次拖拽结果恢复。中间阅读区不单独保存宽度，它始终取三面板扣除后的剩余值。

文件选择后不自动弹出文件树或终端，避免阅读和输入时发生布局跳动。中心宽度压到 `60px` 后，用户可直接拖回分隔条，或使用 Header 现有的文件树/终端按钮折叠对应侧栏，让中心自动恢复。

### 增量候选方案

1. 将 `App.tsx` 现有“外层文件树 + 内层阅读区/终端”的两层横向布局扁平为单一三面板横向布局：`sidebar | main-content | terminal-panel`。
2. 文件树移除固定 `480px` 最大值；拖动左分隔条时使用中心 `60px` 下限，右侧终端不参与缩放。
3. 右侧终端不设置最大宽度；拖动右分隔条时使用中心 `60px` 下限，文件树不参与缩放。
4. 中间阅读区不设置默认比例、最大宽度或独立持久化宽度，只作为两侧当前宽度之间的剩余区域；它允许缩小到 `60px`。
5. 文件树保留现有的宽度与折叠持久化，但删除 `220px–480px` 中的上限裁剪；终端新增“最近一次非零宽度”和折叠状态持久化。
6. Header 左右两个常驻切换按钮继续作为恢复入口：折叠任意一侧后，中心立即吞并空出的宽度；再次打开时恢复该侧最近一次宽度。
7. 可选增加“双击分隔线恢复首次种子宽度”的快捷恢复，不增加中间占位按钮，不触发文件选择后的自动展开。

该方案中的“无限扩大”受当前窗口宽度、另一侧当前宽度和中心 `60px` 下限共同约束；在这三个约束内不再设人为最大值。

### 集中优化验收条件

- 文件树可以超过当前 `480px` 宽度，直到终端当前宽度和中心 `60px` 被保留。
- 右侧终端可以向左拉宽，直到文件树当前宽度和中心 `60px` 被保留。
- 拖动任一侧分隔条时，另一侧面板宽度不发生被动变化。
- 中间阅读区在任何拖拽结果下保留至少 `60px`，允许用户主动将注意力完全交给任一侧面板。
- 关闭左侧或右侧面板后，中间视口自动占用剩余空间。
- Header 两个切换按钮可以恢复对应面板，并恢复最近一次正常宽度。
- 重启应用后，文件树和终端宽度保持用户最近一次布局；中间视口自动适配窗口。
- 文件选择、打开文件、终端输出都不会自动改变三栏宽度。

### 当前结论

问题已完成记录和方案判断，当前没有修改代码，等待晚间集中优化。

## 问题 005：HTML 文件缺少原始脚本与交互式渲染预览

### 现象

当前 `.html` 和 `.htm` 文件会进入普通 `EditorPane`，只能阅读或编辑源码，无法直接查看最终页面。用户需要直接渲染 HTML，并且 HTML 内原始 JavaScript、交互事件、模块脚本、相对 CSS、图片、字体、`fetch` 数据请求和页面内跳转都可以执行。

### 当前代码定位

`src/modules/editor/FileViewer.tsx` 只会把 `getPreviewKind()` 识别到的媒体和大文本分流给 `FilePreviewPane`。HTML 不在 `ASSET_EXTENSIONS` 或 `TEXT_PREVIEW_EXTENSIONS` 中，因此始终进入 `EditorPane`。

现有架构已经具备核心渲染链路：

- `FilePreviewPane.tsx` 已通过 `fs_allow_asset()` 和 `convertFileSrc()` 用 iframe 预览 PDF。
- `src-tauri/tauri.conf.json` 已启用 `assetProtocol`，范围为 `**`，并允许 `asset:` 作为 iframe 来源。
- Markdown 已有独立的 `rendered/raw` 标签状态、视图切换和 dirty 限制，可作为 HTML 的交互模型参考。

### 最佳解决方案

新增语义明确的 `HtmlTab`，与 `MarkdownTab` 平行，而不把 HTML 混入通用 `EditorTab` 的临时预览字段：

```text
HtmlTab
├─ kind: "html"
├─ path
├─ viewMode: "rendered" | "raw"
└─ dirty
```

`.html` 和 `.htm` 默认以 `rendered` 打开，右上角提供与 Markdown 一致的 `Rendered / Raw` 切换：

| 模式 | 实现 | 行为 |
|---|---|---|
| Rendered | `HtmlPreviewPane` + iframe | 直接执行页面 JavaScript，保留 HTML 原始交互 |
| Raw | 现有 `EditorPane` | CodeMirror 源码编辑、保存、检索和替换 |

渲染 iframe 使用原始本地资源地址：

```text
fs_allow_asset(path)
convertFileSrc(path)
iframe src={assetUrl}
```

iframe 不使用 `srcDoc`，也不注入或重写 HTML 字符串。直接加载原文件能保留浏览器基准 URL，因此以下相对资源可按 HTML 所在目录自然解析：

- `<link href="./style.css">`
- `<script src="./app.js">` 与 `<script type="module">`
- `<img src="./image.png">`
- `fetch("./data.json")`
- 字体、视频、音频、页面内链接和交互组件

HTML iframe 不添加 `sandbox` 限制，确保原始 JavaScript、脚本模块、表单和页面交互按浏览器语义执行。

### 交互与刷新策略

1. Raw 模式可继续使用现有编辑器保存流程。
2. Raw 中存在未保存修改时，`Rendered` 切换按钮禁用并提示“保存后预览”，避免切换导致未保存缓冲丢失。
3. 保存完成、文件监测事件或用户点击刷新时，使用递增 `reloadKey` 重新挂载 iframe，并给根 asset URL 增加缓存参数，强制重新加载 HTML、脚本和样式。
4. 只有当前激活的 Rendered HTML 标签挂载 iframe；切走或关闭后卸载，避免交互页面和定时器长期占用内存。
5. Rendered 模式不接管全局文本检索与替换；用户切换 Raw 后沿用当前 Header 搜索与替换能力。

### 涉及的最小改动面

- `src/modules/tabs/lib/useTabs.ts`：新增 `HtmlTab`、打开规划、视图切换状态。
- `src/modules/spaces/lib/serialize.ts`：保存和恢复 `HtmlTab.viewMode`。
- `src/app/components/EditorCompareView.tsx`：在 Raw 时进入编辑器栈，在 Rendered 时进入 HTML 预览栈。
- 新增 `HtmlPreviewPane` 与 `HtmlStack`，复用 Markdown 视图切换和活动标签卸载模式。
- `src/app/App.tsx`、关闭保护、工作区切换保护和搜索目标：补充 `HtmlTab` 的 raw dirty 状态及 rendered 行为。

不需要新增 Rust 文件读取命令、第三方浏览器内核、HTML 解析库或 PDF/网页渲染依赖。

### 集中优化验收条件

- 打开 `.html` / `.htm` 默认显示真实页面，而非源码。
- 页面内 JavaScript、按钮、输入框、图表、模块脚本和动态 DOM 正常执行。
- 相对 CSS、图片、字体、脚本、JSON 数据和其他同目录资源正常加载。
- Raw 模式保留现有 CodeMirror 编辑、保存、搜索和替换。
- 未保存源码不会被切换到 Rendered 覆盖或丢失。
- 外部文件变化与手动刷新可重新加载页面内容。
- 非激活 HTML 页面不保留 iframe，避免后台脚本与页面持续占用资源。
- 双阅览器中 HTML 可独立在左右任一阅读区打开，不影响其他标签。

### 当前结论

问题已完成记录和最佳方案设计，当前没有修改代码，等待晚间集中优化。

## 问题 006：全文折叠快捷键需要改为单组合键

### 现象

当前 CodeMirror 默认全局折叠使用 `Ctrl+Alt+[`，全文展开使用 `Ctrl+Alt+]`，组合键较难按压，也不符合 Codev 当前追求的极简阅读交互。单个代码块通过左侧折叠栏即可操作，当前待解决重点为当前文件的全文折叠与全文展开。

### 复现路径

打开 Markdown Raw、Python 或 R 文件，将编辑器焦点放在中部阅读区，尝试使用全局折叠快捷键。

### 当前代码定位

- `src/modules/editor/EditorPane.tsx`：`basicSetup` 已启用 `foldGutter: true`，同时继承 CodeMirror 默认 `foldKeymap`。
- `@uiw/react-codemirror` 内置默认映射：`Ctrl+Alt+[` 调用 `foldAll`，`Ctrl+Alt+]` 调用 `unfoldAll`。
- Markdown Rendered 使用独立预览组件，全文折叠需要由活动阅读器统一转发到对应视图。

### 用户确认的解决方案

统一改为当前活动阅读器内的单组合键：

- `Ctrl+K`：全文折叠。
- `Ctrl+L`：全文展开。

快捷键只在支持折叠的当前阅读区获得优先级，不影响侧栏、终端和顶部搜索框。单个代码块的左侧折叠栏继续保留。双阅览器时仅操作当前获得焦点的阅读器。

Raw 模式调用 CodeMirror 原生 `foldAll / unfoldAll`；Markdown Rendered 通过预览视图的轻量折叠状态保持标题大纲；R 脚本沿用 `{ ... }` 折叠服务。全文折叠仅在用户触发时执行，不增加常驻扫描。

### 风险与处理

`Ctrl+L` 在部分编辑器中可能承担“选择当前行”等功能，因此需要限定快捷键作用域，并让全文展开命令在支持折叠的文件类型中优先执行。未进入支持折叠的阅读区时不拦截该快捷键。

### 集中优化验收条件

- Markdown Raw、Markdown Rendered、Python、R 文件中，焦点位于阅读区时 `Ctrl+K` 能全文折叠。
- 同一文件按 `Ctrl+L` 能恢复全文。
- 不再要求使用 `Ctrl+Alt+[` / `Ctrl+Alt+]`。
- 单块折叠、搜索定位、文本选择和双阅览器互不受影响。
- 终端、侧栏、搜索框中的 `Ctrl+K` / `Ctrl+L` 保持原有行为。

### 当前结论

已按用户确认增量记录方案，本轮未修改代码，等待集中实现与回归测试。

## 问题 009：Windows 终端纯文本剪贴板链路失效并误触发 Pi 图片粘贴

### 现象

在 Codev 终端中选中文本后复制，PowerShell 执行 `Get-Clipboard -Raw` 无法读到文本；将内容粘贴到 Pi TUI 时出现 `Failed to paste image: no image on clipboard`。同一份文本经 Windows Terminal 复制后可以正常进入 Pi，并显示类似 `[paste #1 +29 lines]` 的文本粘贴提示。

- `src-tauri/capabilities/clipboard.json` 的 `platforms` 仅声明 Linux，因此 Windows 没有原生文本读写权限。
- `src/modules/terminal/lib/rendererPool.ts` 的复制判断要求 `Ctrl+Shift+C`；选区状态下普通 `Ctrl+C` 没有复制分支，会继续发送 `^C` 给 PTY。

将 Tauri 原生剪贴板能力扩展到 Windows，复制和读取统一采用“原生优先、Web Clipboard 备用”，保留真实错误日志，不再静默吞掉失败。

### 集中优化验收条件

- Codev 选中文本后按 `Ctrl+C`，PowerShell `Get-Clipboard -Raw` 能读到完整纯文本。
- Codev 复制内容粘贴到 Pi 后显示文本粘贴提示，不再进入图片失败提示。
- 有选区时 `Ctrl+C` 不向 PTY 发送 `^C`；无选区时 `Ctrl+C` 仍能中断运行中的命令。
- `Ctrl+V`、`Ctrl+Shift+V` 均能粘贴纯文本，多行内容保持换行。
- `Alt+V` 的 Pi 图片粘贴能力不被 Codev 错误拦截。
- 普通 Windows Terminal、PowerShell、Pi TUI、Codev 终端之间的复制粘贴互通。
- 不新增常驻进程；原生剪贴板插件只在复制/粘贴时调用。

## 问题 012：服务类前台命令 Ctrl+C 后无法恢复结束态

### 现象

在 Codev PowerShell 终端运行 `shiny run app.py --port 2398` 等长期服务后按 `Ctrl+C`，服务已经打印 `Shutting down`、`Application shutdown complete` 和 `Finished server process`，终端仍没有恢复清晰的命令结束态或 PowerShell 提示符。普通单进程 TUI 通常可以在 `Ctrl+C` 后自然退出，因此问题主要集中在服务程序及其进程链。

### 当前代码定位

- `src/modules/terminal/lib/osc-handlers.ts` 的 `registerPromptTracker()` 只在收到 OSC 133 `D` 或下一次 `A` 时把命令状态改为结束。
- `src/modules/terminal/lib/useTerminalSession.ts` 的 `commandRunning` 没有 Ctrl+C 后的校正机制；若 PowerShell 没有重新输出提示符标记，该状态会持续为 `true`。
- `src-tauri/src/modules/pty/mod.rs` 已有 `pty_has_foreground_job`，但 Windows 只通过 `shell_has_children(shell_pid)` 检查 Shell 是否存在直接子进程，而且该接口目前只参与隐藏终端的渲染器释放判断。
- PTY 的 `onExit` 只在 PowerShell Shell 自身退出时触发，不能代表其中运行的 Shiny、Uvicorn、Node 服务等前台命令结束。
- `Finished server process` 属于应用日志，不能直接作为进程已经完全退出的系统证据；服务仍可能处于清理、父进程等待或提示符标记丢失阶段。

### 候选解决方案

保留 OSC 133 作为正常命令生命周期的主要信号。无选区按下 `Ctrl+C` 时，在发送 `\x03` 的同时给当前 Session 标记一次 `interruptPending`，随后仅执行有限次数的前台进程校正，例如 300ms、1000ms、2500ms：

1. 若收到 OSC 133 `D/A`，立即结束运行态并取消剩余检查。
2. 若 Windows 前台进程树已经为空，主动将 `commandRunning` 和输出活动态清零，恢复终端静态状态。
3. 若进程仍存在，保持运行或“正在停止”状态；用户再次按 `Ctrl+C` 时继续发送标准中断，不自动强杀进程。

Windows 进程判断需要从“仅看 Shell 直接子进程”调整为递归检查 Shell 后代进程，避免服务包装器、Python 子进程和重载进程造成误判。新命令开始、终端关闭或 Shell 退出时统一取消校正定时器。

该方案不解析 `Finished server process` 等特定日志，不针对 Shiny 写专用规则，也不增加常驻轮询；只有用户按下 `Ctrl+C` 后短时执行最多三次轻量进程检查。

### 集中优化验收条件

- Shiny/Uvicorn、Node 开发服务器及其他长期服务按 `Ctrl+C` 后，进程树结束时终端在约 2.5 秒内恢复结束态。
- PowerShell 正常返回提示符时优先使用 OSC 133 `D/A`，不等待进程校正计时结束。
- 服务仍在清理或仍有子进程时不虚假显示结束，也不自动终止用户进程。
- 再次按 `Ctrl+C` 可以继续向仍存活的前台程序发送标准中断。
- 普通 Pi、vim 等 TUI 的退出、IME 输入、复制粘贴和终端活动动画不受影响。
- 无 Ctrl+C 操作时不运行额外进程轮询，不增加常驻 CPU 和内存负担。

### 当前结论

## 问题 013：搜索结果中的子文件夹无法展开

### 现象

在文件树搜索框中命中子文件夹后，点击或按 Enter 只能选中该结果，无法看到该文件夹的子内容，也没有普通文件树中的展开箭头。搜索到文件时可以继续打开文件，问题集中在目录结果。

### 当前代码定位

- `src/modules/explorer/ExplorerSearch.tsx` 的 `SearchHit` 虽然携带 `is_dir`，但 `handleSelect()` 只对文件调用 `onOpenFile()`；目录结果只调用 `onSelectPath()`，没有连接 `tree.toggle()` 或 `tree.expand()`。
- `src/modules/explorer/RootTree.tsx` 的普通目录行通过 `EntryRow -> actions.toggle(path)` 展开，搜索结果绕过这条树状态链路，因而不会改变 `expanded` 和 `nodes`。
- `RootTree.tsx` 在 `isSearchActive` 时隐藏普通树区域。即使目录数据被异步加载，搜索列表自身也没有渲染子树的位置，用户仍然无法看到展开结果。
- `src/modules/explorer/lib/useFileTree.ts` 目前只有单路径 `toggle/expand`，没有“展开根目录到目标路径并定位”的统一操作。
- `src-tauri/src/modules/fs/search.rs` 已返回正确的绝对 `path`、相对 `rel` 和 `is_dir`，当前证据不支持把后端搜索扫描作为根因。

### 候选解决方案

给搜索结果增加目录专用的 `onRevealDirectory(path)` 回调，并让它复用文件树状态：

1. 在 `useFileTree` 增加一次性 `revealPath(path)`：校验路径属于当前根目录，按“根目录 → 中间父目录 → 目标目录”的顺序展开并加载，只展开必要的祖先链，不递归展开全部后代。
2. `RootTree` 将 `revealPath` 传入 `ExplorerSearch`。搜索目录点击或 Enter 时先选中目标，再关闭搜索状态，回到普通树视图，等待目标行出现后滚动定位。
3. 多根目录搜索需要由 `FileExplorer` 按命中路径路由到所属根目录的 `RootTreeHandle`，避免在当前根树中展开另一个项目的路径。
4. 普通文件树点击、右键菜单、搜索文件打开逻辑保持不变；搜索目录右键菜单保持现有语义。

### 集中优化验收条件

- 搜索命中顶层目录时，点击或 Enter 后退出搜索并展开该目录。
- 搜索命中多层子目录时，所有必要父目录自动展开，目标目录子项可见并滚动到目标位置。
- 多项目搜索命中其他根目录时，能够在正确的项目树中展开，不出现空白或错误项目加载。
- 目录展开只读取目标路径链，不预加载无关后代，不增加常驻搜索开销。
- 文件搜索打开、Ctrl/⌘ 多选、右键复制路径、添加工作区和普通树展开不回归。

### 当前结论

已完成搜索目录不可展开的前端链路定位与增量记录。本轮未修改源码，等待集中实现 `revealPath`、搜索关闭回树和多根目录路由后回归验证。
